## Recurring cosmetic anomalies — check here before reporting a "finding"

- **The global `spanish_civil_war` flag is never cleared on SCW resolution.** `scw_over` / `nationalist_victory` / `SPR_franco_won` are the authoritative end markers; the war flag still being set says nothing about the war still running (seen resolved-but-set in `31eaf7e6`).
- **`ww2_*` theatre flags carry last-seen dates, not first-set dates.** They are re-stamped on every on_action fire, so their set-dates are useless as a war timeline — use the war/peace flags instead. (In `66d6b53c` all three read 1945.3.1.)
- **Double Trotsky flags** appear in SOV flag blocks; harmless duplication, not a political-path bug.
- **`atomic_research_completed` firing ~1940 is a research-tree marker, not a bomb.** It marks the research step, not weapon availability — do not report early nukes off this flag.
- **`production` stores equipment by numeric variant id.** A name grep (`--grep "tank"`) on the `production` section only hits MIO idea names — resolve `equipment_variant_index` via the top-level `equipments={}` registry before concluding a line doesn't exist.
- **`lend_lease_to_allies_history` misses `send_equipment` transfers.** The WA relief system moves stock instantly without touching the diplomacy IC ledger; zero ledger IC between two countries is NOT evidence of no equipment flow — check `creator=` tags in the recipient's stockpile.
- **`units` line count absorbs the navy** — never use it as an army-size proxy; run `savegame.py army <TAG> <saves...>` instead.
- **`division={` blocks appear in TWO sections.** `units` holds deployed divisions; the `xp_by_template` blocks under `experience_status` are siblings of `units`, not nested inside it. A whole-country-block count over-reports — USA at 1944.1 in `911bed3c` is 97 total vs **80 deployed**; SOV 1942.6 is 409 total vs **373** deployed. **Use `savegame.py army`, which does the `units` scoping for you**; do not hand-count. It also prints the two cross-checks, which are not equivalent: `wa_tlm_comp_div_total` equals the units-only count (49/49 tag×date cells on `911bed3c`; one 1-division monthly-sample lag seen on GER 1946.4), while `num_armies_for_training` tracks it only while the army is stable and **overstates during losses** (ITA 1946.4: 28.0 vs 16 deployed). Use the TLM metric for analysis — but it is WA_TLM, so gameplay logic must never read it.
- **A state block omits `controller=` when the controller is the owner.** Taking the field literally makes a country look like it controls only its conquests (ENG 1946.4 reads 3 controlled states instead of 75). `savegame.py buildings` defaults controller to owner; any ad-hoc `states={}` parsing must do the same.
- **`decision_status` `days` and `count` are different clocks and different populations.** `active_timed_decision` exists only while live and carries `days` (remaining mission time when `state=active`; a re-arm cooldown, on an unrelated clock, when `state=failed` or `re_enable_cooldown`). `random_item` carries `count`, a **monotone cumulative fire counter** — that is the field for "how many times did this fire". Two entries were conflated twice in one session; `savegame.py decisions` labels the kinds apart.
- **`capitulated=yes` at depth 3 is a wargoal property, not capitulation.** It appears inside `<TAG>/diplomacy/wargoals` for countries that are perfectly healthy. Only a **depth-2** `capitulated=` is the country's own status.
- **`resource@X` reads `to_use[0] + to_use[2]` — net available MINUS unmet demand.** Not `produced`, and **not `net` alone**. `savegame.py resources` prints it as the **EFFECTIVE** column. ENG aluminium 1942.6: net `807.3`, deficit `−799.0`, effective **`+8.3`** — a `> 50` latch correctly stays shut on a row whose net column reads 16× the bar. Two mistakes stack here and both have cost a scoring session: reading `produced` alone (nearly a false FAIL on R25) and reading `net` alone (**a false accusation against Fix 39, see R32**). *This entry previously said "net available" and cited ENG **bauxite** in the same save, whose deficit is −1.0 so the two readings coincide — a rule induced from the one resource where they agree.* Verified 2026-08-13 on `02bd4445`: 36 discriminating latch cells, all siding with net+deficit, none with net.
- **`obsolete=yes` in the `equipments={}` registry is descriptive, never causal.** It does not mean only-one-per-archetype (288 (creator, archetype) groups on `02bd4445` hold 2+ non-obsolete members, up to six) and it does **not** gate production — 7.0% of lines and 9.6% of assigned factories run obsolete-flagged equipment in the final save, rising through the campaign, incl. USA's 68-factory `tank_usa_medium_chassis_3`. Also: the registry carries **no `archetype` field** (resolve it from `common/units/equipment/`), `obsolete=no` never occurs (absence = non-obsolete), and the entry's `parent_id` is a design-variant pointer unrelated to the def-level `parent =`. Never conclude "the AI cannot build X" from this flag.
- **`production_upgrade_desire_offset` is not serialized into a country's `ai` section.** No `ai_strategy` entry in a save carries a negative value at all, and no `id=` is ever an equipment token; three ungated controls (incl. `SOV_dont_build_shit_guns`) are equally invisible. A save can therefore never answer "did this strategy arm" — score it on the production lines instead. The `ai`-section reading used for R34's `invade` suppressions does not generalise to this type.
- **`date="1.1.1.1"` in `technology/technologies` is a tech being researched right now, not a duplicate.** It carries `research_points` and no `level=`, plus a twin under the sibling `technology/slots` block. Grepping names across the whole `technology` section reports a false duplicate for every in-progress tech (ENG 6, GER 6, USA 3 on `02bd4445`, matching `slots` 1:1). Start-granted techs carry a real date (`1936.1.1.12`).
- **`wa_ai_overext_dbg_active` is a monotone months-active counter, not a boolean.** Read it as "months the overextension flag has been set", not "currently overextended".
- **This mod sets `AIRBASE_CAPACITY_MULT = 100`, not vanilla's 200** (`common/defines/05_defines.lua:173`). `wa_ai_uk_air_dbg_capacity`'s ×100 is therefore the true engine figure — do NOT "correct" it to 200. (An earlier version of this file claimed the opposite.)
- **`*_dbg_started` counters over-count where the queue-growth guard is missing.** They increment after `WA_AI_PC_start_project`, which declines silently on `queue_max`/dedup. The theatre air-base strategy has the guard; the UK-hosting one does not. Never read such a counter as "projects built" — cross-check against actual building levels.
- **Absent `*_dbg_*` counters mean "never incremented", not "missing instrumentation".** The `WA_AI_supply_line_dbg_*` and `WA_AI_overext_dbg_mic_redirects_*` families are bare `add_to_variable` counters with no zero-init, so absence is a *result*, not a probe gap. Contrast the `WA_TLM_*` metrics, which ARE zero-initialised (`WA_TLM_core.txt:61-62`) — there, a present-and-0 value is a real zero reading. **Per-counter semantics — what each one counts, what it does not, and its known miscounts — now live in `documentation/WA_TLM_TELEMETRY_SYSTEM.md` §2.1; read the row before scoring any `*_dbg_*` value.**
- **Cloud campaigns reuse filenames and overwrite each other.** Saves are named `YYYY.M_Mon.hoi4`, so a new run silently replaces the previous campaign's files in place, leaving a few stragglers with *later* in-game dates than the current run's final save. Group by `game_unique_id`, never by filename or date.
- **Infantry-equipment stockpiles must be summed by ARCHETYPE, not by the vanilla family.** GER builds no `infantry_equipment_*` at all — its rifles are `ger_inf_*` — while BUL and ROM have **no** national family and *do* appear as `infantry_equipment_N` with `creator="BUL"`/`"ROM"`. A vanilla-only filter therefore looks plausible on the recipients and silently returns ~0 on the donor: it produced "GER holds 549 rifles" against a true **101 033** in one `9a4cd657` pass. Resolve ids through the top-level `equipments={}` registry, select on `archetype = infantry_equipment`, and keep `heavy_infantry_equipment` (the `*_hv_inf_*` families) broken out separately — merging the two is what made two contradictory passes look reconcilable.
- **The `strategic_air` walk must count `count=` only at the direct child depth of `air_wings={`.** A second `count=` family one level deeper (per-wing history/data sub-blocks) inflates plane totals by ~2.2× and dumps most of the fleet onto one arbitrary state — it produced ENG 27 638 instead of 6 144 on the first `9a4cd657` pass.
- **`WA_port_demolished` is not a Nero-only marker.** The generic `scorch_earth` decision (`common/decisions/_generic_decisions.txt:2927`) sets the same flag as the on_action (`100_wa_on_actions.txt:3336`), so it appears on SOV states from 1941.7, Sicily/Salerno 1943.7–9 and Libya 1944.4 — 19 states at 1944.6 and 26 at 1946.3. A whole-map census of the flag cannot detect a ROOT-gate leak (R21 criterion 3).
- **A campaign can pass every delivery probe and still lose the theatre.** `9a4cd657` placed the Mulberries on spec, capped Nero, landed the designed 33 divisions in Normandy — and the beachhead was German again by 1944.9.1. When an outcome item fails, check the *basing* and *reinforcement* items before re-opening the delivery ones.
- **Air wings are NOT nested inside `air_base` blocks.** The layout is `strategic_air → <TAG> = { air_wing_pool = { air_base = { id = N } air_wings = { count= tag= mission={ strategic_region= } } } }`, and the ~600 `air_base` blocks that carry `state=` are **siblings that appear FIRST**. Attributing wings to "the last `air_base` seen" silently dumps the whole world's air force onto one arbitrary state. Basing requires a **two-pass join**: build `air_base id → state`, then map `air_wing_pool.air_base.id → state`. Carrier decks are the `air_base` blocks with `carrier=` and no `state=`. Depths: `air_wings` at 3, `count=`/`tag=` at 4, `strategic_region=` at 5, equipment `amount=` at 6. This is **distinct from, and compounds with**, the note above about counting `count=` only at the direct child depth of `air_wings={`.
- **Idle carrier aircraft do NOT sit in the equipment stockpile.** The unassigned stockpile holds 1-258 carrier planes for every country at every date in `02bd4445` — essentially nothing — while **JAP holds 7,000 carrier aircraft off-deck, bound into air wings parked at land air bases**, against 1,380 deck slots. A "who over-produces carrier aircraft" query keyed on the stockpile alone returns a confident **false negative**; measure `stockpile + off-deck wings` against total deck capacity. Also note GER/ITA/SOV hold small static carrier-plane stocks (61 / 5 / 93) with zero carriers and zero carrier factories ever — inert holdings that pollute any stockpile-keyed query.
- **A decoy `countries={` block appears at depth 3 BEFORE the real top-level one** (seen at line ~1 101 690 of `af003548`'s `1944.8_Aug.hoi4`). A parser that seeks the first `countries={` and reads country blocks from there lands inside a nested structure and returns garbage or nothing; anchor on depth 1. (2026-08-15)
- **Naval-invasion orders are NOT under `countries/<TAG>`.** They live in the top-level `theatres → theatre → orders_group → order_instance` block. A per-country extraction sees no invasion plans at all and reads as "no live plan" — R34 leg 1's plan half and R44 legs 2/3 must be scored from that block. (2026-08-15)
- **A province omits `controller=` when its controller equals the state's controller** — the province-level twin of the state-block rule above. Any per-province controller read (R50's Narvik probe, corridor holdings) must default a missing `controller=` to the enclosing state's controller, which itself defaults to the owner. (2026-08-15)
- **A production line omits `active_factories=` when it is 0.** Summing `active_factories` over lines silently drops the zero-factory lines from the count of *lines*; a line with `requested_factories` and no `active_factories` is a live but unfunded line, not a parse gap. (2026-08-15)
- **`savegame.py tlm` mis-renders `wa_tlm_pc_built_by_type^N` as a ring-buffer series** — the indexed variable is a per-building-type array (index = building type id), not a time series, so the tool's history axis is wrong for it (33/40 vs 7 seen on `af003548`). - **`wa_tlm_nav_convoys` / `num_equipment@convoy` / `has_equipment = { convoy … }` read the FREE convoy pool, not the fleet.** Any country actually running trade sits at 0 free convoys because every hull is assigned; ENG read 0 for 46 consecutive months on `a232d96c` while its fleet never dropped below ~600. The fleet is `convoys={ equipment={ … creator= } }` at depth 1 of the country block (sum the `equipment` entries; `creator=` tells own-built from exile/lend-lease hulls). `convoys_destroyed=` at country depth 1 is kills **by** that country (= `wa_tlm_nav_conv_killed`), not its own losses.
